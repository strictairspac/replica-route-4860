# 收货地址拆分 · 新旧客户端并存演练

把一笔收货地址从整段字符串拆成「街道 + 门牌」两个字段的灰度期，演示旧客户端（整段地址）
与新客户端（街道/门牌分列）如何共用同一批订单。零三方依赖：Python 标准库 + 原生 HTML/JS，
数据落本地 JSON 文件，事件全部追加存储。

## 启动

```sh
cd address_demo
python3 -I server.py            # 默认 8080，可用 PORT 改
# 浏览器打开 http://localhost:8080
```

测试：

```sh
python3 -I -m unittest discover -s tests -v   # 引擎规则单测（10 项）
python3 -I tests/e2e_api.py                   # 端到端 API 测试（36 项，需先起服务）
```

## 需求与实现对照

| 演练要求 | 实现机制 | 可见位置 |
|---|---|---|
| 旧端改整段、新端改门牌可并发 | 每次写带 `expected_version` 做乐观锁 CAS；版本过期返回 `version_conflict(409)`，互不覆盖 | `engine.write` |
| 迟到旧写不能盖掉已确认门牌 | 新端写门牌即确认（`house_confirmed=true`），此后旧端整段写被 `house_locked(409)` 拒绝 | `engine.write` |
| 重试不重复生效 | 每个写带 `request_id`，服务端幂等表记录首次结果（含拒绝）；同 ID 重放原响应，事件不追加 | `engine.idempotency` |
| 响应丢失重试 | `simulate_lost` 让事件先落库再回 503；重试命中幂等，版本/位点不增长 | 页面「模拟响应丢失后重试」 |
| 无法拆分的旧地址 | **选择暂存（stash）而非拒收**，理由见下 | `engine._stash` |
| 副本追上写入但没换格式 | 新端副本读返回 `format_not_migrated(409)`，`extra.fallback=primary`，明确回主库；旧端在同副本照常读整段 | `engine.read_replica` |
| 回退旧版照常读写 | 模式事件 `mode_switched` 切 v1：新端写被闸门拒绝，旧端整段读写正常，改动标 `dirty` | `engine.switch_mode` |
| 再升级不丢记录，含已确认门牌 | 事件溯源：状态全部由追加日志投影；再升级重放日志，dirty 订单重新转换，`house_locked` 保证确认门牌未被旧写改动 | `engine._project` |
| 页面编排全流程 | 模式/副本控制、订单表、并发写、读写、回退、事件日志、5 个一键剧本 | `static/index.html` |

订单状态机：`legacy`（待转换）→ `split`（已拆分，门牌待确认/已确认）／`stashed`（暂存冲突，
人工处置后回到 `split`）。

## 关键设计取舍：无法拆分时为什么暂存而不是拒收

- **拒收的代价**：订单是上游已成立的交易，地址只是履约信息。拒收会把格式问题升级成交易失败，
  旧客户端又无法自行修复分列字段，客户侧表现为「下单被退回」。
- **暂存的做法**：接单一律成功，整段原文先入库；转换/旧端写入遇到拆不动的地址，订单进入
  `stashed`，同时生成一条人工处置任务（页面「人工处置任务」区可见）。
  - 对**接单**：零影响，订单号正常生成、原文可查。
  - 对**新版读地址**：主库读得到 `stashed` 态和原文（不返回假的街道/门牌）；副本读返回
    `stashed_on_replica` 并指引回主库走人工处置，避免下游按空门牌发货。
  - 人工填入街道/门牌后订单恢复 `split` 且门牌直接置为已确认。
- 如果业务上改为**拒收**策略，差异点也很明确：`migrate_order`/旧端写分支把 `202 + stashed`
  换成 `422` 拒绝且不产生订单变更；代价是接单接口需同步前置校验，本演练保留暂存为默认。

## 副本读路由的三种去向

1. 副本位点落后、订单尚不可见 → `replica_lagging(409)` → 回主库。
2. 位点追平但格式仍是 `legacy` → `format_not_migrated(409)` → 回主库（**追平写入 ≠ 完成格式迁移**，
   两个动作在页面上是独立按钮）。
3. 暂存订单在副本上被读到 → `stashed_on_replica(409)` → 回主库人工处置。
副本离线 → `replica_down(503)`。旧端读只认整段地址，legacy 副本即可服务，不受格式迁移影响。

## 一键剧本

页面右上角 5 个剧本，每个都自动重置后按节奏执行，预期内的拒绝以黄色提示展示：

- **完整剧本**：接单 → 升级 → 拆分/暂存 → CAS 冲突 → 门牌确认 → 迟到旧写被锁 → 幂等重试
  → 副本追平/换格式/读路由 → 回退 → 再升级。
- **并发+迟到旧写**、**无法拆分暂存**、**副本读路由**、**回退再升级**：单点规则的最小复现。

## 文件

```
address_demo/
├── engine.py            # 事件溯源内核：拆分/CAS/门牌锁/幂等/暂存/模式/副本投影
├── server.py            # 标准库 HTTP 服务与 JSON API
├── static/index.html    # 编排页面
├── static/app.js        # 前端逻辑与剧本
├── tests/test_engine.py # 引擎单测
├── tests/e2e_api.py     # API 端到端测试
└── data/state.json      # 运行后生成的持久化快照（事件+幂等表+副本状态）
```

局限：单机内存锁 + 文件快照，演示并发语义而非真实多节点竞争；拆分正则覆盖常见中文地址
（门牌=首个阿拉伯数字到串尾），复杂地址一律走暂存人工处置，不做猜测式拆分。
